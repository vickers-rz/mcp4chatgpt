## 1. [P1] OAuth token 端点未验证客户端密钥及 redirect_uri

位置：`src/mcp4chatgpt/oauth.py:248–279`。

注册返回 `token_endpoint_auth_method=client_secret_post` 并生成密钥，但 `issue_token` 仅检查授权码所属 client_id、过期时间以及可选 PKCE/resource；不验证 client_secret，不比较授权时保存的 redirect_uri，也不验证 grant_type。

复现：注册固定 callback 的客户端，正常授权得到 code，再提交错误的 client_secret、不同 redirect_uri 和错误 grant_type，仍成功得到 access_token。未启用 PKCE 时，取得授权码的一方不需要注册客户端的密钥即可兑换；启用 PKCE 时仍需正确 verifier，不能据此声称可绕过 PKCE。

建议：按注册的认证方法校验密钥，并校验 grant_type 和 redirect_uri，保持校验与一次性消费授权码的并发语义一致。添加错误密钥、缺失密钥、redirect 不匹配的回归测试。

## 2. [P1] 同步命令超时只确认组长退出，可能永久等待子进程

位置：`src/mcp4chatgpt/local_ops.py:102–116,139–142`。

`_kill_process_group` 发 SIGTERM 后，只要 `proc.poll()` 表明直接子进程退出便立即返回，没有检查其进程组。若孙进程忽略 SIGTERM 并持有 stdout/stderr，随后无 timeout 的 `communicate()` 会一直等待 EOF；进程也可能继续修改文件。

复现：Python 父进程 fork 一个忽略 SIGTERM、持有管道并存活 4 秒的子进程，调用 `_run_process(..., timeout_sec=1)`，实际约 4.02 秒才返回 TimeoutExpired。若子进程不退出，此路径没有后续时限。

建议：检查整个进程组，宽限期结束后对仍存活的组发送 SIGKILL；收尾等待也要有界。可参考 durable jobs 的进程组清理实现。

## 3. [P1] Git 重命名会绕过 coding task 的声明路径限制

位置：`src/mcp4chatgpt/workspace/coding_tasks.py:165–188,191–203`。

两处路径枚举均使用默认重命名检测的 `git diff --name-only`。Git 把变更识别为 rename 时，只报告目的路径，源路径的删除未纳入 declared_paths 检查。候选验证及 integrate 的已提交路径检查共享这一遗漏。

复现：task 仅声明 `renamed.txt`，在 task worktree 执行 `git mv other.txt renamed.txt`，之后用 `true` 验证。返回 `validated=True`、`committed_paths=['renamed.txt']`，但未声明的 `other.txt` 已删除。

建议：使用 `--no-renames` 枚举新增/删除路径，或解析 `--name-status -z` 并检查重命名两端；同时修复工作区和提交差异的两条检查路径。

## 4. [P1] 审计日志轮转竞争会使已执行操作返回失败

位置：`src/mcp4chatgpt/audit.py:17–45`；调用后传播位置 `src/mcp4chatgpt/tools.py:1976–1990`。

HTTP 服务使用多线程，同一个 AuditLogger 的检查、选名、rename、gzip、append 却没有互斥。两个请求同时跨过轮转阈值时，可同时选中同一源文件与目标文件，导致 FileNotFoundError，或对同一归档相互覆盖。异常还会从 handler 已经返回后的审计步骤传播，使有副作用操作已经完成却无法正常返回结果，诱发调用方重试。

复现：准备达到轮转阈值的临时日志，用 Barrier 使两个 `log()` 同时执行 rename，结果为一个成功、一个 FileNotFoundError。操作后错误传播由 `_invoke_tool` 的执行顺序确认。

建议：把轮转与写入串行化；跨进程共享日志时还需文件锁或单写入进程。审计写失败应保留操作已经完成的事实，避免把普通日志故障变成可安全重试的业务失败。

## 5. [P2] 验证启动窗口崩溃后，任务没有可用的恢复路径

位置：`src/mcp4chatgpt/workspace/coding_tasks.py:878–931,1154–1157`。

实现先持久化 running 状态，再 Popen，最后记录 pid/pgid。如果进程在 running 已落盘、PID 尚未落盘的窗口崩溃，重试验证会要求 reconcile；但 reconcile 又因缺少 PID 报 `coding_task_validation_process_identity_unknown`。即使明确指定 abandon 并确认已审查副作用，仍无法解除状态；task 文件写入和发布也被 unresolved validation 阻止。

复现：在 `write_task` 已持久化 validation_running、尚无 pid 时注入 SystemExit，随后执行已确认的 abandon，得到上述错误。该具体复现中验证命令根本没有启动。

建议：设计可持久识别的 supervisor/启动握手，或提供明确且保守的人工恢复机制。不能简单把所有缺 PID 的 running 状态当作未启动，因为另一崩溃窗口中命令可能已经执行。

## 6. [P2] 多轮验证中恢复某文件到基线会导致任务卡住

位置：`src/mcp4chatgpt/workspace/coding_tasks.py:556–570`。

准备候选时根据相对固定 base_commit 的最终差异决定 git add 路径。第一次验证已产生 candidate commit 后，如果把某文件恢复为 base 内容，它虽然相对当前 HEAD 有修改，却从该列表消失，无法被暂存。其他文件可以已经提交，最后仍因 worktree 不干净拒绝验证。

复现：声明 app.txt 与 other.txt；修改 app.txt 后验证成功；把 app.txt 恢复 initial，同时修改 other.txt，再以新 operation_id 验证，返回 `coding_task_candidate_worktree_not_clean`，留下 ` M app.txt`。

建议：把“相对 HEAD 待暂存的修改”与“相对 base 的最终范围检查”分开；暂存所有合法的当前修改，再验证最终候选范围。

## 7. [P2] 不同 principal 的同名任务共用发布 ref

位置：`src/mcp4chatgpt/workspace/coding_tasks.py:484`。

task_key 与 worktree 记录按 principal/workspace 隔离，但 task_ref 只使用 task_id。同一仓库的两个 OAuth client 创建相同 task_id 时，共享 `refs/mcp4chatgpt/tasks/<task_id>`。一个发布后，另一个的首次发布必定冲突，即使两个任务本应独立。

复现：client a、b 创建 task_id=same，分别修改 app.txt 并验证；两者 task_ref 相同。a 发布成功，b 得到 `coding_task_publish_conflict: expected missing, found <a 的提交>`。

建议：发布 ref 纳入 task_key 或 principal/workspace 的稳定哈希；迁移时考虑既有 ref，并避免把其他 scope 的 ref 当成本任务发布证据。
